### 材质有专门的灯光、阴影与遮罩配置

`player-main_Material_StencilRT.mat` 的实际保存值包括：

- `_ReceiveLighting = 1`
- `_ReceiveShadow = 1`
- `_UseEmission = 1`、`_EmissionMapOn = 1`
- `_StencilRef = 128`、`_StencilOp = 2`
- 渲染队列2450，关键字含 `_RECEIVESHADOW`。

另外两份 InsideMask/OutsideMask 材质保存了不同的 stencil 比较值，并且其 `_ZWrite` 保存为0。因此不能把这套渲染概括为“所有2D对象、所有pass一律写深度”。实际效果还取决于被使用的 shader pass、材质选择以及运行时改写。

该包同时包含 SpriteRenderer、MeshRenderer、MeshFilter、Camera、Light 和粒子组件等序列化对象。Catalog还声明了31个FBX路径、176个 `.skel.bytes` 路径和202个 `.atlas.txt` 路径；这些是该目录范围内的声明数量，不等于全部已加载角色或可见模型数量。

### 游戏代码对场景表现做了额外工作

补充 CIL 读取覆盖9个目标类型、93个方法，详见 `supplemental-cil.json`：

| 功能 | 实际代码证据 | 能说明什么 |
| --- | --- | --- |
| 面向相机 | `BillboardFacingCamera.Update`，方法 token `0x060008E8`，IL偏移 `0x59` 调用 `UnityEngine.Transform.LookAt`，前序读取相机旋转与forward/up | 不是单纯把平面图贴在任意固定角度；该组件对齐相机朝向。不能证明每个角色均挂载它。 |
| 地面阴影位置 | `ShadowLockToGround.LateUpdate`，token `0x06005BAD`，读取与重写 Transform.position | 代码将position.z归零，使用本游戏自己的坐标约定；不能套用“Unity地面一定是XZ平面”的假设。 |
| 接收阴影 | `EnableRecieveShadowsSpriteRenderer` 中的更新逻辑设置renderer接收阴影 | 游戏有针对精灵渲染的阴影处理，实际启用范围仍需实例/运行时核对。 |
| 面向切换 | `SimpleFlipSpineOnFacing.LateUpdate`，token `0x06005C4D`，IL偏移 `0x4D` 调用 `Spine.Skeleton.set_ScaleX` | 至少这一实现使用Spine骨架的水平镜像控制朝向，不需要把整个角色替换成3D模型。 |
| 动画更新优化 | `SkeletonAnimationLODManager.Update`，token `0x06005D82`，调用Renderer.bounds、GeometryUtility.TestPlanesAABB和ManualSkeletonUpdater.Update | 对可见性和骨架更新有专门管理；“所有东西都动态”需要调度与裁剪，而非每帧无差别更新。 |

IL偏移按补充文件中的 `il_offset` 解释；metadata token仅对上述SHA-256构建有效。主程序并没有在解析过程中被执行。

`SimpleSpineAnimator` 还提供了更直接的动画制作证据：

- `Update`（`0x06005CCB`）读取 StateMachine.facingAngle、NorthMoving/SouthMoving及斜向移动引用并调用 AnimationState.SetAnimation；例如北向移动分支的调用位于 IL+0x36D。
- `set_Dir`（`0x06005CCA`）在符合状态条件且配置 TurnAnimation 时，先 SetAnimation(TurnAnimation)，再 AddAnimation(Moving)，最后改变Skeleton.ScaleX。这里同时使用了方向过渡动画与镜像，不能将其简化成所有角色仅做水平翻转。
- `UpdateAnimFromState`（`0x06005CA6`）包含 SetAnimation、AddAnimation 与 TrackEntry.set_MixDuration，说明有状态驱动、动作排队与混合。
- `FlashWhite`（`0x06005CB0`）检查闪光无障碍设置，并通过 MaterialPropertyBlock 的 SetColor/SetFloat 与 Renderer.SetPropertyBlock 实现反馈；实际颜色取自 WarningColour，不能仅凭方法名说一定是纯白闪光。
- `SpineEventHandler`（`0x06005CC8`）将Spine事件名传入游戏事件。它提供事件接入点，但本次未据此证明具体音效、脚步或伤害绑定。

另一个边界：`PlayerShadowOverlay` 的基类是 `BlendModes.UIImageExtension`。不能因名字有Shadow，就把它当作角色世界空间阴影投影器。

## 5. 与开发商的一手说明核对

1. [Massive Monster 在 Steam 的开发者回复（2022-08-07）](https://steamcommunity.com/app/1313140/discussions/0/3448087385671383167/?l=english)：说明美术先以2D绘制，再摆入3D世界；二维对象使用深度与朝向相机的处理；使用Spine扭曲网格产生更立体的观感。
2. [Unity 官方对 Jay Armstrong 的采访（2022-10-28）](https://unity.com/blog/games/recipe-behind-smash-hit-cult-of-the-lamb)：明确2.5D、用sprites拼接假立体结构、调整角色与相机角度，以及为了2.5D灯光开发定制方案。**这篇采访本身没有提及Spine**。
3. [ACMI 对创意总监 Julian Wilton 的采访](https://www.acmi.net.au/stories-and-ideas/making-games-julian-wilton-massive-monster/)：补充2D绘制、3D空间与shader结合的制作思路。

访谈描述的是作者制作方法；本地静态证据描述的是当前这份构建中的文件和代码。两者相互支持，但不能据此推导未检查的全部shader、实时阴影实现、相机投影参数或所有资产的建模比例。

## 6. 我们当前狐狸样板的真实差距

对现有 `outputs/pet-spine-v0.1/pets/W04/W04.json` 检查得到：11根骨骼、9个插槽、12个region附件、0个mesh附件。四种表情通过完整头部图切换，耳朵、帽饰等没有进一步独立拆分。idle主要使用缩放、平移和旋转。

所以它确实是Spine格式的骨骼样板，但目前完成的只是“拆件能动”。尚未完成加权网格、局部形变、表现转身的绘画/附件、完整动作设计、场景落地、阴影灯光和交互反馈。此前以简单呼吸摆动作为呈现，不能代表Spine能达到的商业制作质量。

对本宠物游戏的建议是先完成一个可验收的精修角色与小型场景标杆，再推广到其他宠物：

1. **角色制作**：精修一只狐狸的头身比例、关节遮挡和握持点；耳朵、尾巴、围巾独立控制，柔性区域使用合适的加权网格。
2. **动作设计**：idle加入重心转移、视线与局部次级动作；战斗动作需要前摇、出手、回收与命中节奏，并配合受击和移动状态。
3. **场景呈现**：二维角色放入受控的2.5D小场景，统一脚底接地点、相机角度、遮挡顺序与阴影表现；灯光/发光效果作为单独的美术任务调试。
4. **环境交互**：根据行为出现落脚尘土、命中特效、武器轨迹与环境响应。背景按层级使用少量风动、光效与粒子，不需要所有物件都使用复杂骨架。
5. **性能与成本**：角色复用骨架规范和动作模板，场景复用模块；根据屏幕可见性和重要性分级更新。2D角色降低部分建模需求，但高质量拆件、绑定、权重和动作仍需要投入制作时间。

上述是针对本项目的设计建议，不是对原作未检查实现的反推，也没有将游戏改为Unity或更改现有宠物资源。
